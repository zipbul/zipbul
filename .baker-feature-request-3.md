# Confirmation + consolidated deliverables — what baker ships for cookie

**To:** `@zipbul/baker` maintainers (github.com/zipbul/baker)
**From:** `@zipbul/cookie`
**Against:** `@zipbul/baker@3.4.0`
**Date:** 2026-06-03
**Follows:** letter 1 (isUint8Array/isByteSize — shipped) + your response to letter 2

## Agreement

Your response to letter 2 is correct on every point, including correcting us:
custom transforms already run at runtime, so "any custom transform, AOT-safe" is
a **zipbul-CLI** serialization issue, not a baker one — we withdraw that from
baker's scope. And `arrayOf` (not `arrayEvery`) already gives per-element,
per-rule diagnostics — we verified it ourselves:

```
@Field(arrayOf(isString, isByteLength(32)))  secrets?: string[]
  blank/short element → { path: "secrets[0]", code: "isByteLength", ... }   // rule code + index preserved
```

So we map `code → reason` (no per-rule `context` needed), and we'll migrate our
own `arrayEvery` usage to `arrayOf` now without waiting.

This letter consolidates the **full list of what baker delivers for cookie**, so
nothing is ambiguous, plus the one design answer you asked for.

## Deliverables baker ships

### D1 — built-in transformers (accepted in your response)

From `@zipbul/baker/transformers`, exported identifiers, sync:

- **`toUint8Array`** — `string` (utf-8) or `ArrayBufferView` → `Uint8Array`.
  Consumer: `kdfSalt: string | Uint8Array → Uint8Array`.
- **`toArray`** — scalar `T` or `T[]` → `T[]`.
  Consumer: `encryptionSecret: string | string[] → string[]`.

These unblock the `deserialize`-owns-everything pipeline AOT-safely today (being
exported identifiers, they also sidestep the CLI issue by construction).

### D2 — `arrayOf` per-element fidelity (docs + regression lock)

No API change — it already works. Your committed action: document `arrayOf`'s
per-element/per-rule `code` + element-qualified `path` semantics versus
`arrayEvery`'s single-`code` AND-predicate, and add a regression test that locks
it. We depend on this guarantee staying stable, so the lock matters to us.

### D3 — `minShannonEntropy(bits)` (accepted, design answer below)

From `@zipbul/baker/rules`, exported identifier, sync, accepts `string` (utf-8
bytes) and `Uint8Array`. Named honestly: docs must state it is a **lower-bound
rejection heuristic** — failing ⇒ definitely weak; passing ⇏ strength. No
`isStrongSecret`. As you noted, an **exported** rule is the only AOT-safe path to
an entropy floor (a local `createRule` is not), so this is not optional for us.

**Design answer — unit: (i) per-symbol H ≥ bits.**

We confirm **(i)**. Rationale, measured against our actual secrets:

```
random 32B base64url   perSymbolH = 4.69 bit/sym   (pass)
"abcdefgh".repeat(4)   perSymbolH = 3.00 bit/sym   (reject)
"ab".repeat(16)        perSymbolH = 1.00 bit/sym   (reject)
"a".repeat(64)         perSymbolH = 0.00 bit/sym   (reject)
```

Per-symbol cleanly separates concerns: **length is guarded by `isByteSize` /
`isByteLength`; uniformity is guarded by `minShannonEntropy`.** Composed in one
field they cover both quantity and distribution, and per-symbol is
length-independent so the two rules don't entangle. (Our current code uses total
`H·N` ≥ 128, but that conflates length and uniformity; we're moving to your (i)
composition.) Docs should state explicitly: **per-symbol, must be paired with a
length rule** — exactly as you proposed.

A concrete floor we'll use: `minShannonEntropy(3)` alongside `isByteLength(32)` /
`isByteSize(16)` rejects all three weak cases above while passing real random
secrets. (The exact threshold is ours to set per field; we only need the rule.)

## Full cookie target (so every deliverable has a consumer)

```ts
deserialize(CookieParserOptionsSchema, rawUserOptions) -> ResolvedCookieParserOptions | issues

secrets?:           arrayOf(isNotEmpty, isByteLength(32), minShannonEntropy(3))   // D2 + D3; code→reason
encryptionSecret?:  transform toArray  + arrayOf(isNotEmpty, isByteLength(32), minShannonEntropy(3))  // D1 + D2 + D3
algorithm:          isIn(['sha256','sha384','sha512']), default 'sha256'
kdfSalt?:           transform toUint8Array + isUint8Array + isByteSize(16), default const   // D1 + 3.4.0
prefixValidation:   isBoolean, default true
httpOnly?/secure?/sameSite?/...: type rules, optional
```

`deserialize` then owns defaults (field initializers + `exposeDefaultValues`),
normalization (D1 transforms), validation (rules incl. D3), and unknown-key
rejection (`whitelist`) — one call, typed object out, no hand-written
resolve/validate.

## Out of baker scope (recorded, not requested here)

- **zipbul CLI**: serialize consumer-*exported* transformers by `importSource`
  (same fix already applied to rules). Needed only for fully-custom transforms;
  D1's built-ins make it non-urgent for cookie. Same root cause as
  `@zipbul/cors`'s local `isMethodsWildcard` `createRule` hazard.

## Summary — baker's checklist for cookie

1. **D1** `toUint8Array`, `toArray` → `@zipbul/baker/transformers` (minor).
2. **D2** `arrayOf` per-element fidelity → docs + regression test (patch).
3. **D3** `minShannonEntropy(bits)`, **per-symbol (i)**, honest naming →
   `@zipbul/baker/rules` (minor, RED-first + triple review + changeset).

That's the complete set. Everything else cookie needs is already in 3.4.0
(`isUint8Array`, `isByteSize`, `arrayOf`, custom transforms at runtime,
`exposeDefaultValues`, `whitelist`, `isIn`, `isByteLength`, `isBoolean`). PRs
welcome for D1 and D3.

— `@zipbul/cookie`
