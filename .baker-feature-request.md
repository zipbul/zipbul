# Feature request — binary (Uint8Array / ArrayBufferView) length & type rules

**To:** `@zipbul/baker` maintainers (github.com/zipbul/baker)
**From:** `@zipbul/cookie` (a sibling `@zipbul/*` middleware)
**Against:** `@zipbul/baker@3.3.1`
**Date:** 2026-06-01

## Summary

baker has no way to validate **binary values** (`Uint8Array` / typed arrays /
`ArrayBufferView`). Every existing length-ish rule rejects them by design, so a
`@Recipe` field that holds raw key material (a cryptographic key, an HKDF salt,
an IV, a nonce) cannot be schema-validated at all today — the only escape is a
locally-defined `createRule`, which (per the AOT codegen contract) has no
`importSource` and is therefore string-literalised by the metadata generator in
a compiled app. So binary validation is currently *un-expressible in an
AOT-safe way*.

We're asking for two small, general-purpose additions.

## Why this isn't already covered (verified against 3.3.1 source)

- `isByteLength(min, max)` — `dist/src/rules/string.js`:
  ```js
  const validateByteLength = (value) => {
    if (typeof value !== 'string') { return false; }   // ← rejects Uint8Array
    const byteLen = Buffer.byteLength(value, 'utf8');
    ...
  ```
  String-only, by name and by implementation. A `Uint8Array` always fails.

- `arrayMinSize(min)` / `arrayMaxSize` — `dist/src/rules/array.js`:
  ```js
  validate: value => Array.isArray(value) && value.length >= min
  ```
  `Array.isArray(new Uint8Array())` is `false`, so typed arrays always fail.

- `isInstance(Uint8Array)` — `dist/src/rules/object.js`: validates
  `value instanceof targetType` but carries **no length constraint**, so it can
  assert *"is a Uint8Array"* but not *"is at least N bytes"*. It also relies on
  the `ctx.addRef(targetType)` ref mechanism rather than an `importSource`-backed
  identifier, which we'd prefer to avoid leaning on for AOT.

- The typechecker family (`isString`, `isInt`, `isBoolean`, `isArray`,
  `isObject`, `isDate`, `isRegExp`, `isFunction`, …) has **no** `isUint8Array` /
  `isArrayBufferView` / `isTypedArray` member.

Conclusion: binary key material is a real, recurring shape (any crypto-bearing
options object has it) and baker simply has no vocabulary for it yet.

## Requested additions

### 1. `isUint8Array` (typechecker)

A bare type-guard rule, mirroring `isString` / `isArray`. Passes iff
`value instanceof Uint8Array`. Belongs in `rules/typechecker.ts` and the `rules`
barrel so it is an **imported identifier** (AOT-safe via the metadata
generator's `ZIPBUL_IMPORT_SOURCE` path).

Optionally a broader `isArrayBufferView` (true for any `ArrayBuffer.isView(v)`)
if you'd rather cover `DataView` and all typed arrays in one rule. For our use
case `isUint8Array` is sufficient.

### 2. `isByteSize(min, max?)` — byte length of a binary value

The binary analogue of `isByteLength`. Validates the **`.byteLength`** of a
`Uint8Array` / `ArrayBufferView`:

```ts
// proposed semantics
isByteSize(min: number, max?: number): EmittableRule
// passes iff ArrayBuffer.isView(v) && v.byteLength >= min && (max===undefined || v.byteLength <= max)
```

Naming is yours to decide — `isByteSize`, `byteLength` (overloaded for binary),
or `isBinaryLength` all read fine; we only care that it's a first-class,
exported, `importSource`-backed rule rather than something each consumer
re-implements with `createRule`. An `emit` that inlines
`v.byteLength` (no allocation) would match the style of the existing
`isByteLength` codegen.

We deliberately are **not** asking for an entropy/key-strength rule — that's a
security policy concern, not a general validator's job, and we'll keep any such
check in our own cross-field step.

## Concrete consumer (so the shape is grounded)

`@zipbul/cookie`'s resolved options carry an HKDF salt as raw bytes:

```ts
// today — manual, because baker can't express it
if (resolved.kdfSalt.length < MIN_KDF_SALT_BYTES /* 16, RFC 5869 §3.1 */) { ...err }

// with the requested rules — schema-expressible, AOT-safe
@Field(isUint8Array, isByteSize(16), { optional: true, context: { reason: CookieErrorReason.InvalidAttribute } })
kdfSalt?: Uint8Array;
```

The same two rules also cover IV length, nonce length, and raw-key length for
any other middleware that validates binary crypto inputs.

## Acceptance notes

- Both rules should be **exported from `@zipbul/baker/rules`** (imported
  identifiers) so the AOT metadata generator emits them as identifiers, not
  string literals — consistent with the fix in zipbul cli commit
  `fix(cli): serialize baker rule decorator args as imported identifiers`.
- Sync (no async), so they compose inside `@Field(...)` like `isInt` / `min`.
- `requiresType` doesn't have a binary option today; if the type-gate optimiser
  needs one, `isUint8Array` as a preceding rule in the same `@Field` can act as
  the gate, or a new `'binary'` `requiresType` could be introduced — your call.

Thanks. Happy to open a PR against `rules/typechecker.ts` + a `rules/binary.ts`
if you'd accept it.
