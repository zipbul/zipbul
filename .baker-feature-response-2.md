## Gap 1 — this is a zipbul-CLI gap, not a baker gap

We have to correct the premise before answering, because it changes who owns the fix.

**baker already supports arbitrary custom transforms, at runtime, with no CLI involved.** `@Field({ transform: { deserialize, serialize } })` stores your function and the sealed executor calls it directly — the generated code is literally `value = refs[i]({ value, key, obj })`, where `refs[i]` is your function reference. `seal()` builds this via `new Function` at app startup. So a local, consumer-defined transformer is **fully functional today** in any runtime-seal environment. It is *not* garbage outside the CLI — it runs.

What "not AOT-safe" actually means is narrower than the letter frames it: the **zipbul CLI's metadata generator** pre-serializes `@Field` decorator args to static form, and it can only reference a value it can `import` — an exported identifier. A local function has no import source, so the CLI string-literalizes it and the transform breaks **on that one build path**. That's a CLI serialization limitation, not a missing baker capability. baker does not depend on the CLI; the CLI consumes baker's metadata.

So the work splits cleanly, and we'll only take the half that's ours:

**Accept — built-in `toUint8Array` + `toArray`.** These belong in baker regardless of AOT: we already curate a transformer library (`trimTransformer`, `jsonTransformer`, …), and these are general one-shape utilities. Exported from `@zipbul/baker/transformers`, so they're imported identifiers — which *also* sidesteps the CLI issue by construction. They cover both your concrete needs (`kdfSalt`, `encryptionSecret`) outright:
- `toUint8Array` — `string` (utf-8) or `ArrayBufferView` → `Uint8Array`
- `toArray` — scalar `T` or `T[]` → `T[]`

**Decline (as a baker feature) — `createTransformer` for AOT-safety.** Adding a factory wouldn't change anything: your function is still defined in your module, and whether the CLI emits it by `importSource` vs string-literalizes it is decided entirely in the CLI. baker bolting on `createTransformer` would be solving a CLI problem in the runtime library and advertising an AOT guarantee we can't keep from here. The correct fix for "my own transform, AOT-safe" is the **same one that fixed rules**: the CLI serializes a consumer-*exported* transformer (or transform object) by `importSource`. That's a CLI change; we'll raise it there. If anything, a thin `createTransformer(name, fns)` could later exist purely to give the CLI a stable tag to match — but that's contingent on the CLI work and we won't ship it as a standalone "AOT fix."

Net: the built-ins unblock your pipeline AOT-safely **today**; the general "any custom transform, AOT-safe" lives in the CLI, not here.

## Gap 2 — already in 3.4.0, via `arrayOf` (not `arrayEvery`)

You flagged this might be a docs clarification. It is. The flattening is specific to `arrayEvery`; `arrayOf` already gives you exactly what you want.

Verified in our source: `arrayOf(ruleA, ruleB)` registers each inner rule as its own per-element rule, and the per-element codegen emits, for every failing element and every failing rule:
```js
errors.push({ path: "<field>[" + i + "]", code: "<that rule's ruleName>", ... })
```
So the failing rule's own `code` survives (`isNotEmpty`, `isByteLength`, a future `minShannonEntropy`) **and** the path is element-qualified (`secrets[2]`). `arrayEvery` collapses to one `code: 'arrayEvery'` because it's an all-or-nothing AND predicate — wrong tool for per-element diagnostics.

Migration (no new API, do it now — don't wait on us):
```ts
@Field(arrayOf(isNotEmpty, isByteLength(32) /* + Gap 3 */))
secrets!: string[];
//   blank  → { path: "secrets[2]", code: "isNotEmpty" }
//   short  → { path: "secrets[2]", code: "isByteLength" }

@Field(arrayOf(oneOf(...)))   // cors
origins!: string[];           // → { path: "origins[2]", code: "oneOf" }
```
(`oneOf` reporting a single `code: 'oneOf'` is correct — it's one OR-constraint; `arrayOf` still gives you the element index around it.)

On the per-rule `context` point: with the per-rule **code** preserved, you map `code → reason` directly — that covers "blank vs short vs weak → distinct reasons" without per-rule `context`. A genuine per-rule `context` channel is a heavier model change we're not taking on speculatively.

Our action: document `arrayOf`'s per-element/per-rule fidelity (vs `arrayEvery`'s single-code semantics) and add a regression test that locks it. Patch, ahead of the rest.

## Gap 3 — `minShannonEntropy`, named honestly — accept

Accepted as a new exported rule, with your naming discipline held: docs will state plainly it's a **lower-bound rejection heuristic** (failing = definitely weak; passing ≠ strength). No `isStrongSecret`. Your self-correction is sound — baker already ships `isStrongPassword`, so an entropy floor isn't foreign.

A note on "optional": you frame Gap 3 as optional because Gaps 1–2 let you express it yourself. But a *local* `createRule` isn't AOT-safe (your own acceptance note), and Gap 1's `createTransformer` doesn't change that for rules — so an **exported** `minShannonEntropy` remains the only AOT-safe path to an entropy floor. We read that as: still worth shipping, not truly optional for you.

**One design call before we build** — the unit of entropy. Shannon `H = -Σ pᵢ·log₂pᵢ` over a byte histogram is **per-symbol** (0–8 bits/symbol): it measures distribution uniformity, not total strength (`"abab…"` scores high per-symbol; a 4-byte uniform string also does). Two readings:
- **(i) per-symbol H ≥ bits** — your literal wording; sound *only paired with a length floor*, which you have (`isByteLength(32)`): length guards quantity, entropy guards uniformity.
- **(ii) total H·N ≥ bits** — meaningful standalone, threshold in absolute bits (e.g. 128).

We lean to **(i)** to match your wording and your length-floor composition, docs stating it's per-symbol and must be paired with a length rule. Confirm (i) vs (ii). (Accepts `string` utf-8 and `Uint8Array`, sync, exported from `@zipbul/baker/rules`.)
