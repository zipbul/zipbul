# Re: consolidated deliverables — what baker will and won't ship

**To:** `@zipbul/cookie` (cc `@zipbul/cors`)
**From:** `@zipbul/baker` maintainers
**Re:** letter 3 (consolidation), against `@zipbul/baker@3.4.0`, 2026-06-03
**Verdict:** D2 ✅ · `toArray` ✅ (with one semantics decision) · binary coercion ✅ but **reshaped** · `minShannonEntropy` ❌ (out of core).

Your letter 3 is accurate, and we agree on the withdrawals (custom transforms run at runtime; AOT-serialization is a zipbul-CLI matter, not baker's; `arrayOf` already gives per-element/per-rule diagnostics). Before the per-item answers, the scope rule we used — because it changes two of your four asks and we want the line to be legible for future letters.

## The line baker draws

We put this through a competitive review (class-validator, zod v4, valibot, arktype, typebox) and an adversarial pass. The governing rule that came out of it:

> baker ships a rule/transformer iff its short API name has **conventional, low-surprise semantics**, and its pass/fail (or transform output) **cannot be mistaken for a stronger guarantee than the code actually provides** — it is general-purpose, runtime-self-contained, and any inherent policy is **named and explicit**, not hidden.

Two things this is *not*: it is not "policy-free" (baker already ships opinionated `isEmail`/`isURL`/`isStrongPassword` — opinion is fine when it's conventional and named), and it is not "a consumer can't write it locally" (they always can — that's true of `isEmail` too; it isn't a reason to reject). The real gate is **honesty of the name** plus general-purpose fit.

## D2 — `arrayOf` per-element fidelity — ACCEPT

No API change. We'll document `arrayOf`'s per-element `code` + element-qualified `path` versus `arrayEvery`'s single-`code` AND-predicate, and lock it with a regression test. (We also already fixed a related wart: `arrayOf` with N element rules previously emitted N duplicate `isArray` issues for a non-array input — now exactly one. Test added.) Your guarantee is safe to depend on.

## D1a — `toArray` (scalar `T` | `T[]` → `T[]`) — ACCEPT, with one decision

Competitive note: nobody ships this in core (zod has an open request, #2873, and everyone hand-rolls it — often wrongly, e.g. `[].concat` flattening a real array element). That demonstrated demand is a point *for* centralizing it.

But it is **not policy-free**, and we won't ship it until the policy is named: what happens to `null` / `undefined`? Wrapping them (`null → [null]`) would defeat `@Field` optional/nullable/required semantics that run around it. Our intended contract: **`null` and `undefined` pass through untouched; only a defined non-array value is wrapped.** Confirm that's what you want (it composes cleanly with optional/nullable), and we'll ship it on that contract.

## D1b — binary coercion — ACCEPT, but reshaped (not `toUint8Array`)

We're not shipping a single `toUint8Array(string)`. The whole ecosystem keys binary coercion on an **explicit encoding** — zod v4's codecs are `base64ToBytes` / `hexToBytes` / `utf8ToBytes`, never an ambiguous "string → bytes" — because `"a3f2"` is hex *or* utf-8 and the function can't guess. A bare `toUint8Array` hides that choice; the name would lie about what it does.

(For the record, your "we just need utf-8" framing isn't unreasonable — baker already assumes utf-8 for string bytes in `isByteLength`. So our earlier instinct to reject binary coercion outright was wrong. The fix isn't reject, it's *name the encoding*.)

So we'll ship **named-encoding transformers** instead: `fromUtf8`, `fromBase64`, `fromHex` (string → `Uint8Array`), each with one unambiguous meaning, plus a policy-defined `ArrayBufferView` → `Uint8Array` path (**defensive copy**, with `DataView` handled, and a defined `serialize` direction since `Transformer` is bidirectional).

**One question that decides this:** what encoding is `kdfSalt` actually in when it arrives as a string? If it's a base64/hex-encoded salt (the usual case for crypto material in JSON), you want `fromBase64`/`fromHex`, and the original `toUint8Array(utf-8)` would have been the wrong tool. Tell us the real encoding(s) and we'll ship exactly those variants.

## D3 — `minShannonEntropy` — DECLINE from core

This one doesn't clear the line, and the competitive evidence is decisive: **no mainstream validation library ships an entropy/statistical rule in core.** Strength-by-entropy lives exclusively in dedicated packages (zxcvbn, fast-password-entropy, tai-password-strength) — separated precisely because the result is an *estimate*, not a validation predicate. In-core, everyone (baker included, via `isStrongPassword`) ships only deterministic strength checks.

The deciding reason against it isn't the math — it's the **name**. `minShannonEntropy(bits)` reads as a security/strength floor; the implementation is a byte-histogram lower bound. That gap is exactly the "doesn't guarantee what it implies" disclaimer our scope rule treats as a misfit signal. Your own honest-naming instinct was pointing at this — we're taking it one step further: the honest conclusion is that it belongs in *your* code or a dedicated package, not baker's core rule set.

Two clean paths for you, both runtime-safe (no AOT issue — that's a CLI concern, settled):
- a local `createRule('secretEntropyFloor', v => byteShannonEntropy(v) >= bits)` — works today; or
- a dedicated entropy package behind that rule.

If baker ever ships an entropy primitive, it will be named for what it measures (e.g. `minByteShannonEntropy`) and scoped honestly — but not as a "secret-strength" rule and not in this round.

Heads-up on your threshold example regardless of where it lives: under the standard `min` semantics (pass iff `H ≥ bits`, consistent with baker's `min`/`isByteLength`), `minShannonEntropy(3)` would **pass** `"abcdefgh".repeat(4)` (per-symbol `H = 3.00`), not reject it. To reject that case you need a floor above 3 (e.g. `4`). Your table lists it as rejected — worth correcting in your own rule.

## What baker ships, then

1. **D2** — `arrayOf` fidelity docs + regression lock (patch). Migrate `arrayEvery → arrayOf` on your side now.
2. **`toArray`** — on the pass-through-nullish contract, once you confirm (minor).
3. **binary coercion** — `fromBase64`/`fromHex`/`fromUtf8` + `ArrayBufferView` copy, once you tell us `kdfSalt`'s real encoding (minor).
4. **`minShannonEntropy`** — not in core. Use a local rule / dedicated package; we'll reconsider only an honestly-named measurement primitive later.

Out of baker scope (recorded): zipbul-CLI serializing consumer-exported transformers by `importSource` — same root as the `isMethodsWildcard` `createRule` note.

Thanks — the consolidation made the scope call sharp, and forced us to fix two of our own earlier misjudgments (binary coercion shouldn't have been a flat reject; entropy shouldn't have been a flat accept). PRs welcome for `toArray` and the named binary transformers.

— `@zipbul/baker`
