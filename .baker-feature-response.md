# Re: binary (Uint8Array / ArrayBufferView) length & type rules

**To:** `@zipbul/cookie`
**From:** `@zipbul/baker` maintainers
**Re:** your request against `@zipbul/baker@3.3.1`, 2026-06-01
**Verdict:** accepted in part — `isUint8Array` + `isByteSize`. Declining `isArrayBufferView` and a new `'binary'` requiresType.

## First, the framing

We want to be straight with you: we're not building this because cookie is blocked. A sibling package being inconvenienced isn't, on its own, a reason for baker to grow an API. The only bar we hold a rule to is *"would a general baker user want this"* — not *"did a consumer hit a wall."*

We're telling you this because it's why the answer is **partial**, not a rubber stamp. We measured each rule against baker's identity (AOT DTO validation, class-validator DX) on its own, independent of your use case. Two passed. Two didn't.

## What we verified

Your reading of 3.3.1 is correct on every point — we re-checked the source:

- `isByteLength` is string-only by implementation (`typeof value !== 'string'` → reject). ✓
- `arrayMinSize`/`arrayMaxSize` gate on `Array.isArray`, which is `false` for typed arrays. ✓
- `isInstance(Uint8Array)` asserts the type but carries no length constraint, and leans on `addRef` rather than an imported identifier. ✓
- typechecker has no `Uint8Array` member. ✓
- `requiresType` has no binary option. ✓

No correction needed. The gap is real.

## Accepted

### `isUint8Array` (typechecker)

Accepted — and to be clear, this one we'd have wanted regardless. It's the empty slot in the typechecker family: same shape as `isRegExp` / `isDate` — `instanceof`, self-narrowing, no typeof gate, zero new mechanism. Lands in `rules/typechecker.ts`, exported from the `rules` barrel, so the AOT metadata generator emits it as an imported identifier. Passes iff `value instanceof Uint8Array`.

### `isByteSize(min, max?)`

Accepted. It mirrors `isByteLength` exactly — `requiresType`-gated where applicable, `constraints: { min, max }`, and an `emit` that inlines `.byteLength` with no allocation. Semantics as you proposed:

```ts
// passes iff ArrayBuffer.isView(v) && v.byteLength >= min && (max === undefined || v.byteLength <= max)
```

We're keeping the name `isByteSize` — it reads as the binary analogue of `isByteLength` without overloading the existing name.

One honest caveat so you can plan: `Uint8Array` isn't a JSON-serializable type, so this lives one step to the side of baker's main `deserialize()`-over-the-wire path. It's still a legitimate DTO shape (msgpack/protobuf-decoded payloads, raw bodies), which is why we're taking it — but it's why it had to clear the bar on its own merits rather than on yours.

## Declined

### `isArrayBufferView` / `DataView` / `isTypedArray` — no

You said `isUint8Array` is sufficient, and we agree. We're not speculatively covering `DataView` and the other typed-array views for a use case nobody has yet. YAGNI. If a concrete need shows up, send another letter.

### A new `requiresType: 'binary'` — no (for now)

This is the one piece of your request that would touch baker's *core* — the type-gate optimiser and the `requiresType` union — rather than just adding two leaf rules. We're not widening the union to save one `typeof` in the generated gate.

Your own letter handed us the smaller path: put `isUint8Array` first in the same `@Field(...)`, and it acts as the gate for the `isByteSize` that follows. That's exactly the pattern we'll document. Your consumer example works unchanged:

```ts
@Field(isUint8Array, isByteSize(16), { optional: true, context: { reason: CookieErrorReason.InvalidAttribute } })
kdfSalt?: Uint8Array;
```

We also appreciate that you pre-emptively scoped out the entropy / key-strength rule (§ "we are not asking for…"). Agreed — that's a security-policy concern, not a validator's. Keep it in your cross-field step.

## Both rules will be

- exported from `@zipbul/baker/rules` as imported identifiers (AOT-safe, consistent with the CLI's identifier-serialization fix);
- synchronous, so they compose inside `@Field(...)` next to `isInt` / `min`.

## Next

We'll implement under our usual discipline — RED-first tests (unit + integration + e2e) before any rule code, then triple review. Target: a minor release. We'll cut you a changeset note when it lands so you can drop the manual `kdfSalt.length` check.

Thanks for the precise, source-grounded letter and for scoping your own ask — it made this easy to say yes to the right half of. A PR against `rules/typechecker.ts` + `rules/binary.ts` is welcome if you'd like to open it; otherwise we'll take it from here.

— `@zipbul/baker`
