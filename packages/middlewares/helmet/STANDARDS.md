# Helmet Standards

**HTTP 응답 보안 헤더 방출자(response security-header emitter)가 지켜야 할 규칙의 정본.**

기능 단위로 규칙을 쌓는다. 각 규칙은 1차 출처(RFC·W3C·WHATWG 원문)만을 근거로 하며, 방출자를 직접 구속하는 규범과 UA 알고리즘에서 파생된 의무를 구분한다.

**대조 기준일 2026-07-12** — 각 규칙의 인용문은 이 날짜의 발행본 원문과 문자 그대로 대조되었다. WHATWG living standard는 이 기준일 이후 변경분만 재대조한다.

**규범 수준 규약**
- **[MUST]/[MUST NOT]** — 원문에 방출자(웹 개발자·conformance checker·sender)를 직접 구속하는 BCP14/동등 키워드가 실재하거나, 위반 시 UA가 헤더를 무시하거나 보호가 소멸하는 하드 실패.
- **[SHOULD]/[SHOULD NOT]** — 원문의 권고, 또는 위반 시 보호가 약화되나 소멸하지는 않는 경우.
- **[무표기]** — 사실·정의·UA 동작 서술. 하드룰로 강제하지 않는다.

## 1. X-Content-Type-Options (MIME 혼동 차단)

- **§1.1** [무표기] 현행 정본은 **WHATWG Fetch §3.6**이다 — 원문이 *"The `X-Content-Type-Options` response header can be used to require checking of a response's `Content-Type` header against the destination of a request"*로 헤더의 역할을 정의한다 [Fetch #x-content-type-options-header]
- **§1.2** [MUST] 이 헤더를 방출한다면 값은 `nosniff` 토큰으로 생성한다 — 원문이 *"Web developers and conformance checkers must use the following value ABNF for `X-Content-Type-Options`: X-Content-Type-Options = \"nosniff\" ; case-insensitive"*로 방출자를 직접 구속하며, **유효한 토큰은 `nosniff` 하나뿐**이다. ABNF가 `; case-insensitive`이므로 대문자 표기도 유효하나 소문자 `nosniff`가 관례다 [Fetch #x-content-type-options-header]
- **§1.3** [무표기] 헤더의 **방출 자체**는 Fetch가 MUST로 명하지 않는다 — 원문은 헤더가 *"can be used"*라고만 하고 서버 대상 방출 의무를 두지 않는다. 방출 권장의 근거는 §1.6의 UA 차단 게이트가 주는 기능적 보안이며, "필수 보안 헤더"는 OWASP 등의 체크리스트 언어이지 Fetch 규범 문구가 아니다 [Fetch #x-content-type-options-header]
- **§1.4** [무표기] UA의 *determine nosniff* 알고리즘은 헤더 값들 중 **`values[0]`만** `nosniff`와 대조한다 — 원문이 *"If values[0] is an ASCII case-insensitive match for \"nosniff\", then return true. Return false"*로 규정하므로, 첫 값이 `nosniff`가 아니면 보호가 적용되지 않는다 [Fetch #determine-nosniff]
- **§1.5** [SHOULD] `X-Content-Type-Options`를 방어적으로 **한 번만** 방출한다 — Fetch는 복수 방출을 금지하지 않는다. get 알고리즘이 값들을 *"separated from each other by 0x2C 0x20, in order"*로 순서대로 결합하므로 `nosniff`를 두 번 방출해도 `values[0]`은 여전히 `nosniff`라 보호가 유지된다. 보호가 소멸하는 것은 §1.4에 따라 **첫 결합 값이 `nosniff`가 아닐 때**뿐이고, 그건 중복이 아니라 §1.2 위반이다 — 단일 값이 의도를 명확히 하므로 한 번만 방출한다 [Fetch #concept-header-list-get·#determine-nosniff]
- **§1.6** [무표기] *determine nosniff*가 true면 UA는 destination이 script-like인데 mimeType이 *"failure or is not a JavaScript MIME type"*이거나 destination이 `style`인데 essence가 `text/css`가 아니면 차단한다 — 원문이 *"Only request destinations that are script-like or \"style\" are considered"*라 하므로 그 밖의 destination은 nosniff가 true여도 차단되지 않으며, mimeType이 **failure(예: `Content-Type` 누락)**여도 차단되므로 정확한 `Content-Type` 방출이 이 보호의 전제다 [Fetch #should-response-to-request-be-blocked-due-to-nosniff?]
- **§1.7** [무표기] nosniff 차단은 응답 status와 **무관**하다 — should-blocked 알고리즘은 response의 header list만 보고 status code를 참조하지 않으므로, 일관된 보호를 위해 방출자는 에러·리다이렉트 응답을 포함한 **모든 응답**에 이 헤더를 방출한다 [Fetch #should-response-to-request-be-blocked-due-to-nosniff?]
- **§1.8** [무표기] ORB·CORB·Sec-Fetch-* 등은 nosniff를 대체하지 않는다 — 기준일 발행본 Fetch **전문 검색**에서 `ORB`·`CORB`·`opaque-response-blocking`은 0건이고 nosniff 차단은 독립 알고리즘이며, Sec-Fetch-*는 서버측 판정용 별개 레이어다 [Fetch 전문 2026-07-12]

## 2. Referrer-Policy (Referer 유출 통제)

**대조 기준일 2026-07-16** — 이 절의 정본은 **W3C Referrer Policy 편집자 초안**(https://w3c.github.io/webappsec-referrer-policy/)과 이를 호출하는 WHATWG Fetch이며, 인용문은 그 발행본과 문자 대조되었다. W3C **TR**(`/TR/referrer-policy/`)은 2017 CR 고정본으로 기본값을 아직 `no-referrer-when-downgrade`로 서술하므로 기본값·문법 판정에는 쓰지 않는다.

- **§2.1** [무표기] 현행 정본은 **W3C Referrer Policy 편집자 초안**(정책·헤더 파싱 정의)이며 **WHATWG Fetch**가 이를 요청 처리에 통합한다. 이 헤더는 전달된 문맥의 referrer policy를 설정한다 — 원문이 *"The `Referrer-Policy` HTTP header specifies the referrer policy that the user agent applies when determining what referrer information should be included with requests made, and with browsing contexts created from the context of the protected resource"*로 헤더의 역할을 정의한다. referrer policy는 요청의 `Referer` 헤더(및 `Request.referrer`)에 담기는 정보량을 정하며, 이는 프라이버시·capability URL 유출과 직결된다 [Referrer Policy #referrer-policy-header]
- **§2.2** [MUST] 이 헤더를 방출한다면 값은 UA가 인식하는 policy 토큰으로 생성한다 — 원문 ABNF는 *"`Referrer-Policy:` 1#(policy-token / extension-token)"*이고 `policy-token`은 *"\"no-referrer\" / \"no-referrer-when-downgrade\" / \"strict-origin\" / \"strict-origin-when-cross-origin\" / \"same-origin\" / \"origin\" / \"origin-when-cross-origin\" / \"unsafe-url\""* 8개다. `extension-token`(*"1*( ALPHA / \"-\" )"*)은 문법을 통과시키기 위한 미래 확장용일 뿐 UA가 정책으로 채택하지 않으므로, **인식되는 정책 토큰은 이 8개뿐**이다. 인식 토큰이 하나도 없으면 파서는 빈 문자열을 반환하여 **헤더가 무시**되고 §2.5로 폴백한다(그래서 [MUST]). 파싱은 소문자 enum과의 동일성 비교이고 nosniff와 달리 case-insensitive 매칭 문구가 없으므로 **소문자로 방출**한다. 값은 따옴표로 감싸지 않는다(원문 Note: *"Referrer-Policy header values should not be quoted"*) [Referrer Policy #referrer-policy-header]
- **§2.3** [무표기] 헤더의 **방출 자체**는 명세가 MUST로 명하지 않는다 — 근거 절(§4.1.1 Usage)은 원문이 *"This section is not normative"*라 명시하며 보호 리소스가 *"can prevent referrer leakage by specifying `no-referrer`"*라고만 서술한다. 방출 의무가 아니라 §2.5의 UA 기본값을 기준으로 한 보안 선택이며, "필수 보안 헤더"는 체크리스트 언어이지 명세 규범이 아니다 [Referrer Policy #referrer-policy-header]
- **§2.4** [무표기] 값에 comma로 나열된 복수 토큰이 있으면 UA는 **마지막으로 인식한 비어 있지 않은 토큰**을 채택한다 — *"parse a referrer policy from a `Referrer-Policy` header"* 알고리즘이 *"For each token in policy-tokens, if token is a referrer policy and token is not the empty string, then set policy to token"*로 각 인식 토큰마다 policy를 덮어쓰므로 **최후 인식 토큰이 승**하고, 미인식·빈 토큰은 채택되지 않는다. 이는 *"loops over multiple policy values to allow deployment of new policy values with fallbacks for older user agents"*—신규 정책을 뒤에 두고 구형 UA용 폴백을 앞에 두는 forward-compat 관용구다(예: `no-referrer, strict-origin-when-cross-origin`) [Referrer Policy #parse-referrer-policy-from-header]
- **§2.5** [무표기] 정책이 지정되지 않았거나 인식 토큰이 없으면 파서는 빈 문자열을 반환하고, 상위 문맥 정책이 없으면 UA는 **기본 referrer policy `strict-origin-when-cross-origin`**을 적용한다 — 원문이 *"The default referrer policy is `strict-origin-when-cross-origin`"*로 규정한다. 이 기본값은 `w3c/webappsec-referrer-policy#142`(2020-11-21 병합)가 이전 기본 `no-referrer-when-downgrade`를 **대체**한 것이며(Fetch #1066은 Fetch가 이 상수를 가리키게 한 배관 변경), 따라서 아무것도 방출하지 않아도 현대 UA는 이미 이 정책을 적용한다. 이보다 약한 정책의 방출은 브라우저 기준선 **아래로** 보호를 낮춘다 [Referrer Policy #default-referrer-policy · #referrer-policy-empty-string]
- **§2.6** [SHOULD NOT] `unsafe-url`을 방출하지 않는다 — 원문이 *"a request's full `referrerURL` is sent along for both same-origin-referrer requests and cross-origin-referrer requests"*로 정의하고 Note가 *"This policy will leak origins and paths from secure resources to insecure origins"*라 경고하여, HTTPS URL의 경로·쿼리를 cross-origin·비보안 출처로 유출시킨다. 명세는 *"The spec does not forbid downgrading to less strict policies"*라 하므로 MUST NOT은 불가하나, §2.5의 안전 기본값을 능동 무력화하므로 방출하지 않는다 [Referrer Policy #referrer-policy-unsafe-url · #downgrade]
- **§2.7** [SHOULD NOT] 구 기본값 `no-referrer-when-downgrade`를 신규 방출값으로 선택하지 않는다 — 토큰 자체는 현역이나 기본값 지위는 §2.5로 대체됐고, 원문 정의상 referrerURL·current URL이 모두 potentially trustworthy이면(예: HTTPS→다른 HTTPS 출처) 전체 URL을 보내므로 현대 기본값 `strict-origin-when-cross-origin`(cross-origin엔 origin만)보다 약하다. 방출 대상 정책은 UA 기본값 이상으로 엄격해야 보호에 의미가 있다 [Referrer Policy #referrer-policy-no-referrer-when-downgrade · #default-referrer-policy]
- **§2.8** [SHOULD NOT] `origin`·`origin-when-cross-origin`을 방출하지 않는다 — 둘 다 downgrade(안전→비안전) 요청에서 referrer를 억제하지 않아 원문 Note대로 *"allows the origin of HTTPS referrers to be sent over the network as part of unencrypted HTTP requests"*인 반면, `strict-origin`계열은 downgrade 시 no-referrer가 된다. 원문이 저자에게 *"Authors wanting to ensure that they do not leak any more information than the default policy should instead use the policy states `same-origin`, `strict-origin`, or `no-referrer`"*라 권고하므로, §2.5 기준선 아래 정책(§2.6의 `unsafe-url`·§2.7의 `no-referrer-when-downgrade`와 함께 `origin`·`origin-when-cross-origin`)은 방출하지 않는다 [Referrer Policy #referrer-policy-origin · #information-leakage]
- **§2.9** [무표기] 복수값 폴백(§2.4)은 `Referrer-Policy` **헤더에만** 정의된 문법이다 — 헤더 ABNF는 `1#(...)` 리스트이나 `<meta name="referrer">`(§delivery)와 요소의 `referrerpolicy` 속성은 각각 **단일 policy 값**만 받는다. 이들 문서·요소 레벨 전달 수단은 응답 헤더 방출자의 범위 밖이다 [Referrer Policy #referrer-policy-delivery]
- **§2.10** [무표기] Referrer-Policy 헤더의 실효는 응답 status가 아니라 소비 문맥에 결부된다 — 파싱·policy container 생성 어디도 status를 참조하지 않고, 특히 **3xx redirect 응답의 헤더는 진행 중 요청의 policy를 갱신한다**(원문 *"If policy is not the empty string, then set request's referrer policy to policy"*, Fetch가 HTTP-redirect fetch에서 이를 호출). 문서·워커·스타일시트 생성 응답과 redirect 응답에서 실효를 가지므로(원문 §7: *"CSS style sheets process `Referrer-Policy` headers, and store a referrer policy in the same way that Documents do"*), redirect를 포함한 모든 응답에 동일 정책을 방출하는 것이 일관 보호를 준다(이미지·스크립트 등 여타 서브리소스의 최종 200 응답에는 무효과) [Referrer Policy #set-requests-referrer-policy-on-redirect · #integration-with-css]
- **§2.11** [SHOULD] Referrer-Policy를 **한 번만** 방출한다 — §2.4가 last-wins이므로, 프록시·후속 미들웨어가 뒤에 붙이는 중복 헤더(또는 헤더 라인)의 마지막 인식 토큰이 의도한 정책을 **조용히 뒤집는다**. nosniff(§1.5)는 `values[0]` 승이라 중복이 무해했지만 Referrer-Policy는 반대이므로, 단일 방출이 §1.5보다 더 절실하다 [Referrer Policy #parse-referrer-policy-from-header]
